Aegis Maritime System – Technical Requirements Document (TRD)

1. Introduction

The Aegis Maritime System is a monorepo that provides real‑time vessel tracking, tactical HUD integration, and LoRa‑based satellite communication for maritime operations. It combines a Node.js backend API, a Next.js dashboard, and ESP32 firmware for on‑board sensors. This document captures the technical requirements necessary to design, develop, and operate the system at production scale.

2. Scope

  • Backend API (Node.js/Express) – ingestion, storage, and analytics.
  • Frontend dashboard (Next.js) – visualisation, command & control, tactical HUD.
  • Firmware (ESP32/LoRa) – telemetry collection, bi‑directional command.
  • CI/CD pipeline – Docker, Watchtower, self‑hosted GitHub Actions.

Out of scope: hardware design of vessels, external third‑party GIS services beyond provided GeoJSON files.

4. Functional Requirements

  1. Vessel Telemetry Ingestion – Receive JSON payloads (lat, lon, speed, heading, status) over UDP/LoRa at up to 10 Hz per vessel.
  2. Data Persistence – Store raw telemetry and derived tracks in PostgreSQL; keep 30‑day retention.
  3. Real‑time Broadcast – Push updates via WebSocket to dashboard clients with < 250 ms latency.
  4. Tactical HUD Integration – Expose `/api/cmd` endpoint for issuing navigation commands to vessels; secure with JWT.
  5. Historical Queries – Provide `/api/fleet` with time‑range filters; support CSV export.
  6. Alerting – Detect out‑of‑bounds, low‑battery, or collision risks; push alerts to Dashboard and optional email/SMS.
  7. Admin UI – Role‑based access (admin, operator, viewer) for configuration and log review.
  8. Internationalisation – UI supports EN and local maritime languages; dates in ISO 8601.

5. Non‑Functional Requirements

  • Performance – System must handle 5 000 concurrent vessels, 50 000 WebSocket subscribers, and sustain 1 000 API requests/s.
  • Scalability – Horizontal scaling via Docker Swarm/Kubernetes; stateless API servers behind an L7 load‑balancer.
  • Reliability – 99.9 % uptime SLA; automatic container restart; data replication with PostgreSQL streaming and Redis Sentinel.
  • Security – TLS 1.3 for all HTTP/WS traffic; JWT (RS256) for auth; rate‑limit 100 req/min per IP; input validation on all endpoints.
  • Observability – Export Prometheus metrics; centralised logging with Loki/Grafana.
  • Maintainability – Code coverage ≥ 80 %; CI linting, type‑checking (TypeScript), automated tests.
  • Compliance – GDPR‑compatible data handling; ship‑level anonymisation on public APIs.

6. Data Model

Key tables (simplified):

CREATE TABLE vessels (
  id UUID PRIMARY KEY,
  name TEXT NOT NULL,
  imo VARCHAR(9) UNIQUE,
  mmsi VARCHAR(9),
  vessel_type TEXT,
  created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);

CREATE TABLE telemetry (
  id BIGSERIAL PRIMARY KEY,
  vessel_id UUID REFERENCES vessels(id),
  ts TIMESTAMP WITH TIME ZONE NOT NULL,
  latitude DOUBLE PRECISION,
  longitude DOUBLE PRECISION,
  speed_knots REAL,
  heading REAL,
  battery_percent REAL,
  raw JSONB
);

8. Security Architecture

  • Network segmentation: firmware ↔ LoRa gateway ↔ DMZ ↔ API.
  • Secret management: Docker secrets for DB credentials, JWT private key.
  • Audit logging: immutable logs stored in separate S3 bucket.
  • Pen‑testing scope defined in separate security‑review document.

9. Performance & Scalability

  • Benchmark target: 1 ms average DB insert per telemetry point.
  • Cache latest vessel state in Redis (TTL 5 s) to minimise DB reads.
  • Horizontal auto‑scaling trigger on CPU > 70 % for API containers.

10. Deployment & DevOps

  • Docker‑compose for local dev (backend, db, redis, dashboard).
  • K8s manifests for prod (namespace a‑maritime, rolling updates).
  • GitHub Actions workflow: lint → test → build → push Docker image → deploy via Helm.
  • Watchtower updates containers automatically on new image tag.

11. Testing Strategy

  • Unit tests (Jest) for backend services – 80 % coverage.
  • Integration tests (Supertest) against API.
  • E2E tests (Playwright) for dashboard UI.
  • Hardware‑in‑the‑loop simulation for firmware (Arduino CLI).
  • Load testing with k6 – simulate 5 k vessels and 10 k WS clients.
