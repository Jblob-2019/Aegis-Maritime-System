Aegis Maritime System – Product Requirements Document (PRD)

1. Vision & Purpose

Enable maritime operators to monitor, command, and respond to vessel movements in real‑time, improving safety, situational awareness, and operational efficiency across commercial, military, and research fleets.

2. Target Market & Stakeholders

  • Commercial shipping companies (fleet managers, logisticians).
  • Naval and coast‑guard agencies (tactical commanders, surveillance units).
  • Research institutions tracking marine wildlife.
  • Maritime IoT device vendors (partner integration).

3. Personas

  • Operator – Uses the dashboard to view vessel tracks, issue commands, and respond to alerts.
  • Administrator – Configures system settings, manages users, and oversees deployments.
  • Field Engineer – Programs ESP32 devices, validates LoRa connectivity, and collects sensor data.

4. Success Metrics

  • 95 % of telemetry points displayed within 250 ms latency.
  • 99.9 % system uptime per quarter.
  • Reduction of vessel‑incident response time by ≥ 30 % compared to legacy AIS dashboards.
  • Adoption: ≥ 5 major maritime organisations within the first year of release.

5. High‑Level Features (MoSCoW)

Must have
  • Real‑time vessel telemetry ingestion (10 Hz per vessel).
  • Web‑based dashboard with map visualisation, vessel list, and details pane.
  • Command & control UI (send navigation commands to vessels).
  • Alert engine (geofence breaches, low battery, collision risk).
  • User authentication & role‑based access control.
Should have
  • Historical playback of tracks with CSV export.
  • Multi‑language UI (English + two regional languages).
  • Integration with external AIS providers (optional data overlay).
Could have
  • Predictive analytics (machine‑learning‑based ETA predictions).
  • Mobile‑native companion app (React Native).
  • Voice command integration for tactical HUD.

6. User Stories (selected)

1. As an Operator, I want to see all vessels on a map so that I can monitor their positions at a glance.
2. As an Operator, I need to filter vessels by type, status, or region to focus on relevant assets.
3. As an Operator, I want to click a vessel and view its recent track, speed, and heading.
4. As an Operator, I can send a navigation command (e.g., change course) to a vessel and receive acknowledgment.
5. As an Operator, I receive a visual and audible alert when a vessel exits a protected area.
6. As an Administrator, I can create, edit, and revoke user accounts with specific roles.
7. As a Field Engineer, I can upload new firmware to an ESP32 device via the OTA endpoint.
8. As a Field Engineer, I can view realtime telemetry logs from the LoRa gateway for debugging.
9. As a Researcher, I can export a vessel’s track data for the last 24 h as CSV for analysis.
10. As a Administrator, I can view system health dashboards (CPU, memory, DB latency) and trigger a container restart.

7. Acceptance Criteria (example for #1)

  • Map loads within 2 seconds on a standard broadband connection.
  • All active vessels (≤ 5 000) are displayed as icons without overlap. • Icons colour‑coded by vessel type.
  • Hovering over an icon shows a tooltip with vessel name, speed, and heading.

8. Competitive Landscape

  • Existing AIS dashboards (MarineTraffic, VesselFinder) – mostly passive, limited command capability.
  • Naval tactical systems – proprietary, high cost, limited to government.
  • Open‑source vessel‑tracking projects (OpenCPN) – lack LoRa integration and real‑time command.

9. Assumptions & Dependencies

  • LoRa network coverage is available for all target vessels.
  • PostgreSQL 15 and Redis 7 are used in production.
  • Docker Engine 20+ and Kubernetes 1.28 are available for deployment.
  • Third‑party GIS datasets are licensed for commercial use.

10. Constraints

  • Regulatory: Must not store raw AIS data longer than required by local maritime law.
  • Hardware: ESP32 firmware must stay under 256 KB flash.
  • Budget: Initial MVP must be deliverable within $250 k development budget.

11. Timeline (MVP)

  • Sprint 1 (2 weeks): Set up project scaffolding, CI/CD pipeline, Docker environment.
  • Sprint 2 (2 weeks): Backend telemetry ingestion API + PostgreSQL schema.
  • Sprint 3 (2 weeks): Dashboard map UI showing static vessel data.
  • Sprint 4 (2 weeks): Real‑time WebSocket integration, basic command endpoint.
  • Sprint 5 (2 weeks): Alert engine and role‑based auth.
  • Sprint 6 (2 weeks): Firmware OTA update flow, testing, documentation.
  • MVP Release (Week 12): Full functional prototype ready for pilot deployment.
